# 1.2 Password Reset — Status Report

**Status: COMPLETE** (feature branch `feat/password-reset`, off `dev`). Date: 2026-07-21.

Reuses the token + email infrastructure built in 1.1 (`VerificationToken`,
`EmailService`, `VerificationService`) — no new table, no new email transport.

## What was built

### Backend
- `VerificationService.requestPasswordReset(email)` — **enumeration-safe**: issues a
  `PASSWORD_RESET` token and emails a link only if the account exists; silent no-op
  otherwise. Invalidates any outstanding reset tokens for the user first.
- `VerificationService.resetPassword(token, newPassword)` — validates the token
  (purpose / expiry / single-use) and the new password (min 8 chars), sets the new
  BCrypt hash, consumes the token.
- Reset tokens use a **shorter TTL** than verification tokens: `reset-token-ttl-hours`
  default **1h** (vs 24h for student verification).
- Endpoints (both public): `POST /auth/forgot-password`, `POST /auth/reset-password`.
  `forgot-password` always returns the same generic message (no account enumeration).
- Rate limits: `forgot-password` 5/10min, `reset-password` 10/10min (per IP).
- `SecurityConfig` permits both endpoints.

### Frontend
- `AuthService.forgotPassword(email)` / `resetPassword(token, newPassword)`.
- `/forgot-password` page (request a link) and `/reset-password?token=` page
  (set new password, with confirm-match + min-length client checks).
- "Forgot password?" link added to the login page.

### Tests
- `VerificationServiceTest` now **18 tests** (added 8 for reset): token hashing, silent
  unknown-email, short-password rejection, and invalid/expired/used/wrong-purpose token
  paths. All green.

## Verification performed

## Issues / known limitations (by design or deferred)

1. **Password reset does NOT invalidate existing JWT sessions.** The app issues 7-day
   JWTs with no revocation list (cyber-audit #2). So resetting a password does not log
   out an attacker who already holds a valid token until it expires. **Follow-up:** add a
   `tokenNotValidBefore` / token-version field on the user and check it in
   `JwtAuthenticationFilter` (closes audit #2 and makes reset fully effective). Out of
   scope for 1.2; logged here.
2. **No email delivered until SMTP is configured.** Same as 1.1 — with `MAIL_*` unset the
   link is logged, not sent. Must not be promoted to prod expecting real emails until
   Resend SMTP is verified working.
3. **Enumeration-safe UX tradeoff:** a user who typos their email gets the same "if an
   account exists…" message and no error. Intentional (prevents account enumeration).
4. **Min password length (8) is enforced only on reset**, not on original registration
   (register still only requires `@NotBlank`). Consider aligning registration validation
   in a later pass.

## Not blocking merge to `dev`
Merges cleanly; testable on dev via the logged reset link. Prod promotion gated on SMTP

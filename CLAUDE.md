# CurtinHonestly: working agreements for coding agents

`.cursor/rules/project-context.mdc` says what the project is and how it runs. This
file covers the conventions that are easy to get wrong.

## Git

### Authorship and attribution

- Commits are authored by the repository owner, never by an assistant. Before the
  first commit in a clone, run:

  ```bash
  git config user.name devon-clarkk
  git config user.email 168324492+devon-clarkk@users.noreply.github.com
  ```

- Never add `Co-Authored-By`, `Generated with`, session links, model names, or any
  other AI attribution to commit messages, pull request titles or bodies, code
  comments, or documentation. Never append a "generated by" footer to GitHub
  comments or reviews.

### Commit messages

- Conventional Commits: `feat(scope): ...`, `fix(scope): ...`, `chore: ...`,
  `docs: ...`, `build(frontend): ...`. The scope is the area touched (`admin`,
  `frontend`, `db`, `deploy`, `nav`, and so on).
- Subject in the imperative, lower case after the type, no trailing full stop.
- The body explains why in plain prose wrapped at about 76 columns, not a list of
  files. `git log` shows the house style.

### Branching

- `dev` is the integration branch and `main` is production. Both deploy on push.
- Feature work goes on a branch cut from `dev`, named `feat/<name>`, `fix/<name>`,
  `chore/<name>` or `docs/<name>`, and is opened as a pull request into `dev`.
  `dev` is promoted to `main` with its own pull request. Never push feature work
  straight to `main`.
- The word `claude` (or any other assistant name) is forbidden in branch names.
  If a session was started on a branch named that way, do the work on a
  correctly named branch instead and delete the badly named one from the remote.
- The owner merges through the GitHub UI. Do not merge, and do not deploy anything.
- Never rewrite history on a branch someone else may have checked out.

## Backend conventions

- Schema changes that `ddl-auto=update` cannot make go in a Flyway migration; see
  `backend/src/main/resources/db/migration/README.md`.
- Configuration is environment variables with documented defaults in
  `application.yml`, never hardcoded values.
- Anything that sends email goes through `EmailService`, which never throws.
- Unit tests are Mockito service tests. The `@SpringBootTest` suites use
  Testcontainers and fail without a Docker daemon; that is an environment
  limitation, not a regression.

# SEO audit: curtinhonestly.com

**31 August 2026.** Findings against the live production site and this
repository. Measurements were taken against `https://www.curtinhonestly.com` and
the production API.

The technical foundation is in good shape. Unit pages prerender with real review
data, correct titles, descriptions, canonicals, Open Graph tags, and a JSON-LD
graph carrying `Course`, `AggregateRating`, `Review`, `BreadcrumbList`,
`WebSite`, and `Organization`. The sitemap carries per-unit `lastmod` drawn from
the latest review. The apex 301s to `www`, and `www` is what canonicals and the
sitemap declare, so there is no host split.

Three sets of things are fixed here. The rest is a ranked list, and the first
item on it is the one that decides what the others are worth.

---

## Fixed here

### 1. Every unmatched URL served an indexable copy of the home page

Azure Static Web Apps answers a URL with no file behind it by rewriting to
`navigationFallback.rewrite` and returning **200**, not 404. Microsoft's
configuration reference is explicit that route rules do not apply to requests the
fallback handles, and that the fallback returns 200.

The fallback pointed at `/index.html`. Angular's prerender writes the home page
to that filename, so the fallback was not serving a bare shell. It was serving
the fully rendered home page, complete with `<meta name="robots" content="index,
follow">`:

```
curl https://www.curtinhonestly.com/definitely-not-a-real-page-xyz   # 200, 88,286 bytes
curl https://www.curtinhonestly.com/                                 # 200, 88,286 bytes  (byte-identical)
```

Any address a crawler invented or a stale link pointed at became another
indexable near-duplicate of the home page, from an unbounded supply. The
self-referencing canonical to `/` limited the damage, because canonicals are a
strong consolidation hint. But a hint is all it is, and this is the shape that
surfaces in Search Console as soft 404s and "Duplicate, Google chose a different
canonical".

The fix has three parts:

- `frontend/public/staticwebapp.config.json` points the fallback at
  `/index.csr.html`, the bare client-render shell the Angular builder already
  emits alongside the prerendered pages. It is the same document the SSR server
  would return for a `RenderMode.Client` route, so this is the idiomatic mapping
  rather than a workaround. Client routing still resolves every route, and
  `PrerenderFallback.Client` still covers unit codes added since the last deploy.
- `frontend/src/index.html` denies indexing by default, and `SeoService` opts the
  indexable route families back in explicitly.
- Two guards, because the whole thing hangs on a file nobody maintains by hand.
  `scripts/generate-seo-assets.js` fails the build if the source shell stops
  saying `noindex`; `scripts/verify-seo-output.js` runs after `ng build` and
  fails if the configured fallback target is missing or indexable, or if the
  prerendered home page, a unit page, or a faculty hub is not indexable.

### 2. The catalogue had one crawlable entry point, showing 24 of 1,761 units

The sitemap offered 1,761 unit URLs. The prerendered home page linked **24** of
them; the rest of the catalogue arrived through infinite scroll, which is an
`IntersectionObserver` and produces no crawlable links. Past those 24, internal
discovery depended entirely on the prerequisite graph rendered on each unit page:
real links, but sparse and directional. A unit that was nobody's prerequisite and
was not on the home page's first page had no internal links at all.

Sitemaps make pages discoverable. Internal links are what make them worth
crawling and ranking, and a page with no internal links receives no internal
authority.

Five prerendered faculty hubs now cover the whole catalogue:

| Hub | Units |
|---|---|
| `/faculty/science-and-engineering` | 572 |
| `/faculty/humanities` | 501 |
| `/faculty/health-sciences` | 351 |
| `/faculty/business-and-law` | 258 |
| `/faculty/aboriginal-studies` | 79 |

Each hub lists its whole faculty on one page, grouped under the four-letter
subject prefix, with a jump bar across the prefixes. No pagination, so no
page-number URLs and no unit more than one link from its hub. The subject
headings also put the codes students search, `COMP`, `MATH`, `NURS`, into the
page as headings; the largest hub has 61 of them.

The links run both ways. The site footer carries all five hubs, so every one of
the 1,761 unit pages links every hub, and each unit page breadcrumbs home to its
own faculty. Unit-page JSON-LD now has a three-rung `BreadcrumbList` through the
hub, and each hub carries a `CollectionPage` with an `ItemList` of exactly the
units it links.

Verified on a full production build: 1,767 routes prerendered, hubs linking 1,761
units, and every hub link count matching its faculty total exactly.

**Cost.** The largest hub is 471 kB uncompressed, 46 kB gzipped, which is what
ships. About 182 kB of that is the hydration payload and 81 kB the `ItemList`.
The change also adds 4.3 kB to the initial bundle, which was already about 20 kB
over its 500 kB budget. Neither is a problem today; both are worth knowing.

### 3. Second pass: headings, title lengths, duplicate URLs

From a sampling pass over 29 live unit pages.

**Heading levels.** Unit pages went from `h1` straight to seven `h3` section
headings with no `h2`, so the outline skipped a level on the 1,761 pages that
carry the site. The legal pages already did this correctly. The sections are now
`h2` and the five CSS rules that styled them moved with them, so nothing renders
differently: verified against computed styles on the live page.

**Title lengths.** 14 of the 29 sampled titles passed 60 characters, where search
results cut them. Titles now drop the ` | CurtinHonestly` suffix when the whole
thing would overflow, keeping the code, name and review count, which are what
tell the page apart from the handbook's entry for the same unit. Live count after
deploying: 4 of 29, and those four exceed 60 on the unit name alone.

**One URL per page.** `trailingSlash: "never"`. Both `/units/COMP1000` and
`/units/COMP1000/` answered 200 with the same page. The canonical already named
one of them, so nothing was mis-indexed, but the duplicate was still being
fetched. It now redirects.

That last one interacts with the fallback: Microsoft's docs show `never` also
redirecting `/x.html` to `/x`, which is what `navigationFallback` points at. It
was tested on dev before production. The internal rewrite is unaffected, so every
client route still resolves and unmatched URLs still get the `noindex` shell. A
direct request for `/index.csr.html` now redirects to a dead path, which nothing
links.

The same pass found no duplicate titles or descriptions, alt text on every image,
and one `h1` per page.

## Ranked next

### 1. 1,729 of 1,761 unit pages have no reviews on them

This is the finding that reframes the rest.

```
total units:         1761
with >=1 review:       32     (all in Science and Engineering)
with >=3 reviews:       4
total reviews:         47
```

Every one of those 1,761 pages is in the sitemap and indexable. On 98% of them
the unique content is nil: what remains is unit metadata restated from the
official Curtin handbook, which is exactly what
`handbook.curtin.edu.au` already ranks for. That is a large surface of thin,
largely duplicate pages, and Google assesses quality across a site rather than
page by page.

The hubs from the section above are still right, because they fix the crawl graph
whatever the page count is. But "ramping up SEO" over 1,761 pages backed by 47
reviews will meet a quality ceiling, not a discovery one.

Three ways to go, roughly in order of how much they ask:

- **Index what has content.** Gate sitemap inclusion, and possibly indexability,
  on a review threshold. Reviewed units get the full treatment; the rest stay
  reachable and linked but out of the index until they earn it, and roll in
  automatically as reviews arrive. This is the smallest change and the most
  defensible, and the build already knows each unit's review count.
- **Give the empty pages something of their own.** Prerequisite chains, what a
  unit leads to, grade distributions across the faculty. Real, non-handbook
  content that does not need a review to exist.
- **Leave it and grow reviews first.** Defensible if review volume is climbing
  fast. It is the option that most depends on numbers only you have.

Worth deciding before spending on keyword research: which pages you want to rank
is upstream of what you want them to rank for.

### 2. Decide what the `Course` review markup is for

Unit pages emit `aggregateRating` and up to ten `Review` nodes on the `Course`.
Google's `Course` structured data reference documents `name` and `description` as
required and `provider` as recommended; `aggregateRating` and `review` are not
among the documented properties, and `Course` produces a course list or carousel
rather than a review snippet. Expect no stars in Google results from this.

Unsupported properties are ignored rather than penalised, and the markup is
genuinely useful to other consumers: Bing, and the LLM-driven answer engines that
increasingly read JSON-LD directly. So this is a decision, not a defect. Keep it
for those consumers with the expectation set correctly, or restructure.

Confirm before acting either way. Paste a live unit URL into Google's Rich
Results Test and read what it reports as eligible. That is the primary source;
this section is the documentation's claim, not a measurement.

### 3. Fonts are 372 kB, against a 10 kB page

| File | Served |
|---|---|
| RobotoCondensed-VariableFont_wght.woff2 | 169 kB |
| Rubik-VariableFont_wght.woff2 | 110 kB |
| NimbusSanL-Reg.woff2 | 46 kB |
| NimbusSanL-Bol.woff2 | 46 kB |

A unit page is 10 kB gzipped and pulls 372 kB of fonts behind it, which makes
them the site's dominant payload by a wide margin and the first place to look for
a Core Web Vitals win. Sizes at that scale are what a full variable font with
Cyrillic, Greek and Latin Extended costs; a Latin subset of the same faces is
usually a fraction of it.

Not done here, for two reasons worth stating. It regenerates binary design
assets, which is a call for whoever chose the typefaces. And review text is
free-form student writing that can contain any character, so a subset needs
`font-display: swap` to be carrying the fallback properly, which it does today.
Measure before and after with PageSpeed Insights rather than trusting the byte
count alone.

Three typeface families is also a design question worth asking once, since it is
three round trips before the first styled paint.

### 4. Share images are the raw logo

`og:image` is `/assets/images/logo.png` on every page and `twitter:card` is
`summary`, so every link shared to Discord, WhatsApp, or a student group renders
the same small logo. For a site whose growth is student word of mouth, a per-unit
image carrying the unit code, rating, and review count is a direct
click-through lever. It needs a 1200x630 asset per page, so it wants a generator
in the build alongside the sitemap, and `summary_large_image` once real images
exist. Do not switch the card type before then.

### 5. `/compare` is deliberately `noindex`

`CompareComponent` calls `noIndex()`. Defensible for a tool page, but comparison
is high-value search intent and the page is already lazy-loaded and cheap. Worth
revisiting now that the hubs exist to link it from.

## Where the tooling fits

Items 2, 3 and 4 need no tooling: they are decisions. Item 1 needs numbers you
already have plus a judgement call. Everything about **demand** needs OpenSEO and
a DataForSEO key: which unit codes students actually search, whether "unit
reviews" or "course reviews" is the phrasing in Australia, what the competing
pages are. See [`README.md`](README.md) for standing both tools up.

Hub URLs were chosen to be durable and the copy to be cheap to revise, so keyword
data can rewrite the titles and headings without moving a single URL.

## What was measured, and what was not

A full production build was run end to end against the production API: 1,767
routes prerendered, the shell denying indexing, the home page, unit pages and
hubs opting back in, and both guards failing the build when the regressions they
cover are introduced. `index.csr.html` is already deployed, returns 200, carries
the module script that boots Angular, and renders the not-found component when
loaded directly, so the document the fallback will serve is known good. The hub
pages were rendered in a browser against the build output and checked at mobile
width for overflow.

That Static Web Apps serves that document for an unmatched URL comes from
Microsoft's configuration reference, not from an observation, because the routing
only exists once deployed. Confirm it after the next deploy with the request that
found the problem:

```bash
curl -s https://www.curtinhonestly.com/definitely-not-a-real-page-xyz | grep -o '<meta name="robots"[^>]*>'
```

It should report `noindex, nofollow`, and that response should no longer be
byte-identical to `https://www.curtinhonestly.com/`. Then submit the sitemap in
Search Console and watch the hub pages get crawled first: they are the pages that
carry the rest.
